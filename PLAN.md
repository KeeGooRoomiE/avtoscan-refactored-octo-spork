## 3. Флоу: стартовый экран

Один экран перед началом теста, поля сверху вниз:

1. **Фамилия и Имя** — текстовый инпут (`.field-input`)
2. **Должность** — выпадающий список: `МОП`, `ТП`, `Сервис`
3. **Раздел тестирования** — выпадающий список, неактивен до выбора должности, после выбора — фильтруется по должности (конфиг соответствия — см. §9, п.2, ждём от директора)
4. **Почта** — выбор руководителя, которому придёт результат. Список зависит от раздела/должности (паттерн `.manager-btn` + массив `MANAGERS`, свой список для этого проекта — см. §9, п.3)
5. **Кнопка «Начать тест»** — зелёная (`--green`), неактивна пока не заполнены все поля выше (класс `.visible` появляется только при валидной форме, как в референсе)

После выбора должности+раздела клиент сразу подгружает банк вопросов раздела (см. §4) — никакого обращения к Actions на этом шаге, тест стартует мгновенно по клику.

Хедер и футер — на каждой странице приложения (стартовый экран, экран теста, экран результата).

## 4. Пул вопросов, подбор и подсчёт — всё на клиенте

**Решено:** раз банк вопросов всё равно лежит в открытом статике репозитория (см. §8), генерация теста и подсчёт результата делаются **полностью в браузере**, без обращения к GitHub Actions на старте или на сдаче. Это убирает задержку `workflow_dispatch` (5–30+ сек) для этих двух шагов целиком — она остаётся только для отправки письма и для операций редактора вопросов (см. §7–8).

- На раздел — банк из **100–200 вопросов**, хранится как статический JSON в репозитории (`/data/questions/<section>.json`), доступен всем по прямому URL.
- При старте теста клиент:
  1. Забирает `/data/questions/<section>.json` целиком (включая `correct`).
  2. Фильтрует по `position_tags` под выбранную должность.
  3. Перемешивает (Fisher–Yates) и берёт первые **N** (20–30) без повторов.
- Число вопросов N — настройка раздела с дефолтом, не глобальная константа.
- По завершении теста клиент сам сверяет `given` с `correct` по каждому вопросу и считает `score_percent` — сверять не с чем и незачем гонять через сервер, эталонные ответы и так у клиента на руках.
- Типы вопросов (задаются в редакторе на уровне вопроса, см. §7):
  - **single** — один правильный ответ (`.radio-btn`)
  - **multiple** — несколько правильных ответов (чекбоксы, та же карточка, `type=checkbox`)
  - **free** — свободный ответ (текстовое поле). Только ручная проверка руководителем при просмотре письма, в `score_percent` не входит.

## 5. Таймер

- У раздела — поле `timer_seconds` (опционально).
- Глобальный дефолт — **20 минут**, если у раздела свой таймер не задан.
- Таймер идёт с момента показа первого вопроса, по истечении — автосабмит текущих ответов (как есть, без досдачи).

## 6. Модель данных

### Вопрос (банк раздела, хранится в открытом статике вместе с правильным ответом — см. §8 про принятый риск открытости)

```json
{
  "id": "svc-0042",
  "section": "service",
  "position_tags": ["service"],
  "type": "single",
  "text": "Текст вопроса",
  "options": ["Вариант А", "Вариант Б", "Вариант В"],
  "correct": [1],
  "points": 1
}
```

- `type: "multiple"` → `correct` содержит несколько индексов.
- `type: "free"` → вместо `options`/`correct` — `answer_reference` (опционально, справочно для руководителя), проверка всегда ручная (`auto_check` не нужен — автопроверки нет в принципе).
- `position_tags` — какие должности видят этот раздел/вопрос.

### Результат прохождения — самодостаточный токен, не хранится в репозитории

**Решено:** результат не пишется файлом в репозиторий (не нужен `results/<hash>.json`, не нужен поллинг). Сразу после подсчёта клиент кодирует полный снапшот в base64(url-safe) и кладёт его во фрагмент URL — страница результата декодирует его прямо в браузере, без единого сетевого запроса:

```
https://.../result.html#d=<base64(JSON)>
```

Содержимое токена:

```json
{
  "v": 1,
  "result_hash": "uuid-для-удобства-ссылки-на-словах",
  "timestamp": "2026-07-31T12:00:00Z",
  "full_name": "Иванов Иван",
  "position": "МОП",
  "section": "sales",
  "manager_email": "kop5@navi42.ru",
  "duration_seconds": 842,
  "answers": [
    { "question_id": "svc-0042", "text": "Текст вопроса", "options": ["А","Б","В"], "type": "single", "given": [1], "correct": [1], "is_correct": true }
  ],
  "score_percent": 76.7,
  "correct_count": 23,
  "total_count": 30
}
```

- Токен несёт **полный** снапшот вопросов (текст+варианты, не только id) — так ссылка остаётся читаемой сама по себе, даже если банк вопросов раздела потом поменяется.
- **Решено:** ссылка одна и та же для сотрудника и для руководителя, детализация не различается — сотрудник на экране после сдачи сразу видит и % и, по кнопке/ссылке, полный разбор по вопросам, ровно то же самое уходит в письмо руководителю. Отдельного «урезанного» варианта нет.
- **Принятый риск (зафиксировано в диалоге):** раз эталонные ответы публичны и грейдинг клиентский, сотрудник технически может сам собрать себе токен-результат с любым % не проходя тест по-честному. Никакой подписи/проверки на сервере для этого токена нет и не планируется — источником доверия для руководителя остаётся сам факт получения письма от workflow (см. §8), а не ссылка как таковая.
- Free-ответы — в разбивке помечены как «на ручную проверку», в `score_percent` не учитываются.
- Практическое ограничение: 20–30 вопросов с полным текстом в одном base64-блоке может давать длинную ссылку (не проблема для fragment — он никогда не уходит на сервер и не ограничен длиной URL по факту использования, но для «отправить ссылку в мессенджере» может выглядеть громоздко). При необходимости — сжатие payload перед base64 (например, `lz-string`) как деталь реализации, не блокирующий вопрос.

## 7. Редактор вопросов (админка)

- Отдельная HTML-страница по отдельной ссылке (не в навигации основного квиза), форма логина по паролю (модель доступа по аналогии с `wikinest_avtoscan`, пароль хешируется SHA-256).
- **Решено:** пароль — это **чисто UI-заглушка**, а не реальный контроль доступа. Без бэкенда его нельзя проверить по-настоящему: тот, кто достанет embedded-токен из исходников страницы, технически сможет вызвать workflow добавления вопроса напрямую через GitHub API, минуя страницу и пароль. Зафиксировано как принятый риск (см. §8) — доп. проверка passcode внутри workflow сознательно не делается.
- Функциональность:
  - выбор раздела (или создание нового)
  - **добавление вопроса** — форма отправляет данные (текст, тип single/multiple/free, варианты, отметка правильных) как inputs в `workflow_dispatch`, workflow коммитит вопрос в `/data/questions/<section>.json`
  - **редактирование/удаление** существующих вопросов пула — способ (тот же workflow с режимом `mode: add|edit|delete`, или отдельные workflow на каждое действие) **пока не решён**: зависит от итогового формата хранения банка вопросов (один файл на раздел vs. файл на вопрос), решается на этапе реализации §6/§8, не блокирует остальной план.
- UI/стиль — те же классы, что и основной квиз, визуально неотличим от остального приложения.

## 8. Архитектура: один публичный репозиторий, GitHub Pages + GitHub Actions

**Решено (после обсуждения):** идея с двумя репозиториями и урезанными правами токена отклонена — «плевать, одной репой разберёмся, пусть в статике всё лежит». Банк вопросов, включая поле `correct`, хранится **в открытую** в этом же публичном репозитории. Это осознанно принятый риск: технически заинтересованный сотрудник может найти правильные ответы через сырые файлы репозитория или DevTools. Компенсирующих мер (отдельный приватный репозиторий, урезанный токен, скрытие `correct` на этапе выдачи) сознательно не делаем.

### Что лежит в репозитории

- статический html/css/js квиза, стартового экрана, экрана результата
- `header.jpg` / `footer.jpg`
- `/data/questions/<section>.json` — банк вопросов раздела, включая `correct`, читается клиентом напрямую по сырому URL
- `/data/managers.json` (или аналог) — список руководителей по разделам/должностям
- страница редактора вопросов (§7)
- `.github/workflows/`:
  - **workflow добавления/редактирования/удаления вопроса** — вызывается со страницы редактора (§7), коммитит изменения в `/data/questions/<section>.json`
  - **`send-email.yml`** — вызывается клиентом при сдаче теста, принимает результат целиком (ФИО, должность, раздел, %, время, полный разбор по вопросам, ссылку-токен на результат — см. §6) как inputs, шлёт письмо руководителю через SMTP-секреты Actions (паттерн `send_email.py`)

### Больше не нужно (снято по итогам пересмотра)

- отдельный приватный `-bank` репозиторий
- `generate-quiz.yml` / `grade-quiz.yml` и связанный с ними поллинг `runs/<quiz_id>.json` / `results/<result_hash>.json` — генерация и подсчёт теперь на клиенте (§4), задержки `workflow_dispatch` на старте/сдаче больше нет
- urезанный по правам «токен только для триггера без Contents» — теперь не нужен, т.к. скрывать больше нечего

### Токен, встроенный в код страниц

**Решено:** один и тот же embedded fine-grained PAT, scope `Actions: Read and write` на этот репозиторий, используется и на публичной странице квиза (для `send-email.yml`), и на странице редактора (для workflow добавления вопросов). Разделения на «токен пожёстче для админки» не делаем — при одном репозитории и UI-пароле (см. §7) это не даёт реального выигрыша в безопасности.

### Что реально осталось через Actions

Только два случая обращения к workflow_dispatch во всём приложении:
1. Отправка письма руководителю при сдаче теста.
2. Изменение банка вопросов из редактора (добавление/правка/удаление).

Оба — не на пути прохождения теста сотрудником (кроме самого факта отправки письма в конце, где задержка не критична — сотрудник уже видит свой результат на экране мгновенно, письмо уходит асинхронно фоном).

## 9. Что решено / что уточнить у директора

**Решено:**
- Визуальный стиль — 1:1 копия `autoscan-shiny-octo-invention` (цвета, шрифт, хедер/футер, компоненты), кроме кнопки старта — она зелёная (`--green`)
- Архитектура — **один** публичный репозиторий, GitHub Pages + Actions, без VM-бэкенда, без второго приватного репозитория (см. §8)
- Банк вопросов (включая правильные ответы) хранится в открытую в статике — принятый риск, компенсирующих мер не делаем
- Генерация теста (выборка N вопросов) и подсчёт % — полностью на клиенте, без Actions на старте/сдаче
- Actions используется только для: (1) отправки письма руководителю, (2) добавления/правки/удаления вопросов из редактора
- Результат теста — самодостаточная ссылка (данные закодированы в base64 во фрагменте URL), в репозитории не хранится; одна и та же ссылка/детализация и для сотрудника, и для руководителя
- Возможность подделать себе результат без честного прохождения — принятый риск, без крипто-защиты
- Пароль в редакторе вопросов — UI-заглушка, не настоящий контроль доступа; доп. проверка в workflow сознательно не делается
- Один и тот же embedded-токен (`Actions: Read and write` на этот репозиторий) используется и в публичном квизе, и в редакторе
- Типы вопросов: single / multiple / free
- Пул 100–200 вопросов на раздел, выборка 20–30 случайных на попытку
- Free-ответы: только ручная проверка руководителем, в `score_percent` не входят
- Дефолтный таймер: **20 минут**, если у раздела не задан свой

**Нужно уточнить у директора перед/во время разработки:**
1. Итоговый список разделов тестирования и их соответствие должностям (МОП / ТП / Сервис)
2. Список руководителей (ФИО + email) на каждый раздел/должность — по аналогии с массивом `MANAGERS` в референсе
3. Формат хранения банка вопросов (один JSON-файл на раздел vs. файл на вопрос) — от этого зависит, как именно будет устроен workflow редактирования/удаления вопроса (§7) — решается на этапе реализации, не требует решения директора
