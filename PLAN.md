## 1. Контекст

Компания «Автоскан» хочет квиз/тестирование для сотрудников (МОП, ТП, Сервис), по аналогии с уже существующим сервисом-памяткой `autoscan-shiny-octo-invention` (статический GitHub Pages + GitHub Actions для отправки почты, без бэкенда).

**Репозиторий:** `KeeGooRoomiE/avtoscan-refactored-octo-spork` (текущий репозиторий, публичный, remote уже настроен).

**Референс дизайна и подхода к отправке почты:** [`KeeGooRoomiE/autoscan-shiny-octo-invention`](https://github.com/KeeGooRoomiE/autoscan-shiny-octo-invention) — публичный репозиторий, `index.html` + `send_email.py` + `.github/workflows/send-email.yml`. Все точные значения ниже сняты прямо из этого файла.

## 3. Флоу: стартовый экран

Один экран перед началом теста, поля сверху вниз:

1. **Фамилия и Имя** — текстовый инпут (`.field-input`)
2. **Должность** — выпадающий список: `МОП`, `ТП`, `Сервис`
3. **Раздел тестирования** — выпадающий список, неактивен до выбора должности, после выбора — фильтруется по должности (конфиг соответствия — см. §9, п.2, ждём от директора)
4. **Почта** — выбор руководителя, которому придёт результат. Список зависит от раздела/должности (паттерн `.manager-btn` + массив `MANAGERS`, свой список для этого проекта — см. §9, п.3)
5. **Кнопка «Начать тест»** — зелёная (`--green`), неактивна пока не заполнены все поля выше (класс `.visible` появляется только при валидной форме, как в референсе)

Хедер и футер — на каждой странице приложения (стартовый экран, экран теста, экран результата).

## 4. Пул вопросов и подбор

- На раздел — банк из **100–200 вопросов**.
- При старте теста — случайная выборка **20–30 вопросов** без повторов (Fisher–Yates на стороне генератора).
- Число вопросов N — настройка раздела с дефолтом, не глобальная константа.
- Типы вопросов (задаются в редакторе на уровне вопроса, см. §7):
  - **single** — один правильный ответ (`.radio-btn`)
  - **multiple** — несколько правильных ответов (чекбоксы, та же карточка, `type=checkbox`)
  - **free** — свободный ответ (текстовое поле). **Решено:** только ручная проверка руководителем при просмотре письма, в `score_percent` не входит.

---

## 5. Таймер

- У раздела — поле `timer_seconds` (опционально).
- **Решено:** глобальный дефолт — **20 минут**, если у раздела свой таймер не задан.
- Таймер идёт с момента показа первого вопроса, по истечении — автосабмит текущих ответов (как есть, без досдачи).

## 6. Модель данных

### Вопрос (в банке вопросов, хранится вместе с правильным ответом)

```json
{
  "id": "svc-0042",
  "section": "service",
  "position_tags": ["service"],
  "type": "single",
  "text": "Текст вопроса",
  "options": ["Вариант А", "Вариант Б", "Вариант В"],
  "correct": [1],
  "points": 1
}
```

- `type: "multiple"` → `correct` содержит несколько индексов.
- `type: "free"` → вместо `options`/`correct` — `answer_reference` (опционально, справочно для руководителя) + `auto_check: false` (зафиксировано — автопроверки нет).
- `position_tags` — какие должности видят этот раздел/вопрос.

### Результат прохождения

```json
{
  "result_hash": "sha256-или-uuid",
  "timestamp": "2026-07-31T12:00:00Z",
  "full_name": "Иванов Иван",
  "position": "МОП",
  "section": "sales",
  "manager_email": "kop5@navi42.ru",
  "duration_seconds": 842,
  "answers": [
    { "question_id": "svc-0042", "given": [1], "correct": [1], "is_correct": true }
  ],
  "score_percent": 76.7,
  "correct_count": 23,
  "total_count": 30
}
```

- **Проходящему тесту** после сдачи показывается только `score_percent` (и, при желании, `result_hash`). **Не показывать** `answers` с разбивкой — ни на экране, ни в DOM/localStorage/коде страницы.
- **Руководителю** на почту — письмо (паттерн `send_email.py`) с полной разбивкой: вопросы, ответы сотрудника, правильные ответы, итоговый %, `result_hash`. Free-ответы — с пометкой «на ручную проверку», без учёта в %.

## 7. Редактор вопросов (админка)

- Отдельная HTML-страница по отдельной ссылке (не в навигации основного квиза), форма логина по паролю (модель доступа по аналогии с `wikinest_avtoscan`, пароль хешируется SHA-256). Механизм хранения/смены пароля — см. §9, п.5.
- Функциональность:
  - выбор раздела (или создание нового)
  - добавление вопроса: текст, тип (single / multiple / free), варианты ответов, отметка правильного(ых) варианта(ов)
  - редактирование/удаление существующих вопросов пула
- Пишет напрямую в банк вопросов приватного репозитория (нужен отдельный, более привилегированный токен — см. §8, п.3).
- UI/стиль — те же классы, что и основной квиз, визуально неотличим от остального приложения.

## 8. Архитектура: GitHub Pages + GitHub Actions, без отдельного бэкенда

Базовый вариант подтверждён (как у «памятки»), но требование «не хранить сырые данные в странице, чтобы нельзя было посмотреть верные ответы через код элемента» напрямую в этом варианте не решается — обычный паттерн из `autoscan-shiny-octo-invention` (один публичный репозиторий + токен с полным доступом прямо в JS) не годится: если банк вопросов лежит там же, откуда токен может читать контент, сотрудник достанет токен из DevTools и прочитает файл с ответами напрямую через GitHub API.

**Схема (два репозитория + токен с урезанными правами):**

1. **Приватный репозиторий `-bank`** (рабочее имя: `avtoscan-refactored-octo-spork-bank`, **пока не создан** — см. §9, п.1) — хранит:
   - банк вопросов с правильными ответами (`/data/questions/<section>.json`)
   - список руководителей/почт
   - workflows:
     - `generate-quiz.yml` — принимает раздел+должность, случайно выбирает N вопросов, вырезает поле `correct`, коммитит урезанный набор в публичный репозиторий
     - `grade-quiz.yml` — принимает `quiz_id` + ответы сотрудника, сверяет с приватным банком, считает %, коммитит в публичный репозиторий только `{ result_hash, score_percent }`, шлёт полное письмо руководителю через SMTP (паттерн `send_email.py`)
   - секреты Actions: SMTP-логин/пароль отправителя, отдельный PAT с правом `contents:write` на публичный репозиторий (используется только workflow'ами, никогда не попадает в браузер)

2. **Публичный репозиторий `avtoscan-refactored-octo-spork`** (этот) — раздаётся GitHub Pages:
   - статический html/css/js квиза и стартового экрана
   - `header.jpg` / `footer.jpg`
   - `runs/<quiz_id>.json` — сюда `generate-quiz.yml` кладёт вопросы без ответов (клиент читает напрямую по сырому URL)
   - `results/<result_hash>.json` — сюда `grade-quiz.yml` кладёт только `{score_percent}` — клиент поллит этот файл
   - здесь же может жить редактор вопросов (§7), но с отдельным, более привилегированным токеном, встроенным только в код этой отдельной страницы

3. **Токен в коде основной (публичной) квиз-страницы** — fine-grained PAT, scope только `Actions: Read and write` на приватный `-bank` репозиторий, без `Contents` scope. Умеет только «запустить workflow», банк вопросов через него прочитать нельзя даже при утечке из исходников.

4. **Задержка как осознанный компромисс:** `workflow_dispatch` — асинхронный, обычно 5–30 секунд на старт+выполнение (иногда дольше).
   - на старте теста — один запрос на генерацию сразу всего набора вопросов, с индикатором загрузки, пока клиент поллит `runs/<quiz_id>.json`
   - на сдаче теста — аналогично, экран «проверяем результат…» с поллингом `results/<result_hash>.json`
   - **Решено (по итогам обсуждения):** приемлемость задержки пока не подтверждена окончательно — сначала собрать прототип генерации вопросов через Actions и измерить реальную задержку на практике, прежде чем фиксировать архитектуру как финальную.

**Альтернатива, если задержка окажется неприемлемой:** лёгкий бэкенд на уже существующей VM (`wikinest_avtoscan` использует `backend/` с Flask/FastAPI, см. `BACKEND_ARCHITECTURE.md` этого репозитория) — синхронный ответ, банк вопросов физически недоступен клиенту никогда. Технически проще, без хаков с двумя репозиториями и урезанными токенами — к этому варианту возвращаемся, если задержка Actions на практике окажется неприемлемой.

## 9. Что решено / что уточнить у директора

**Решено:**
- Визуальный стиль — 1:1 копия `autoscan-shiny-octo-invention` (цвета, шрифт, хедер/футер, компоненты), кроме кнопки старта — она зелёная (`--green`)
- Архитектура — GitHub Pages + Actions, без отдельного VM-бэкенда (см. §8), с оговоркой про измерение задержки на прототипе
- Типы вопросов: single / multiple / free
- Пул 100–200 вопросов на раздел, выборка 20–30 случайных на попытку
- Результат: сотруднику — только %, руководителю — письмом полная разбивка с хэшем
- Free-ответы: только ручная проверка руководителем, в `score_percent` не входят
- Дефолтный таймер: **20 минут**, если у раздела не задан свой
- Задержка 5–30+ сек на старте/сдаче теста: пока не финализирована, **следующий шаг — собрать прототип генерации вопросов через `generate-quiz.yml` и измерить реальную задержку**, прежде чем принимать решение о варианте с VM-бэкендом

**Нужно уточнить у директора перед/во время разработки:**
1. Создание приватного репозитория `-bank` — пока отложено. Когда понадобится (перед реализацией §8) — уточнить точное имя/владельца ещё раз, если не `avtoscan-refactored-octo-spork-bank` / `KeeGooRoomiE`
2. Итоговый список разделов тестирования и их соответствие должностям (МОП / ТП / Сервис)
3. Список руководителей (ФИО + email) на каждый раздел/должность — по аналогии с массивом `MANAGERS` в референсе
4. Механизм хранения/смены пароля(ей) для страницы редактора вопросов — кто их знает/меняет
